# 異方性反射の黒い斑点に関する調査

ノーマルマップ2ndと異方性反射・リアル光沢を併用した際に発生する黒い斑点について、推定原因、修正案および検証結果をまとめる。

- 不具合報告: [Issue #441](https://github.com/lilxyzw/lilToon/issues/441)
- 修正案: [PR #442](https://github.com/lilxyzw/lilToon/pull/442)
- 調査対象: lilToon 2.4.1（upstream/master: `e698a2f`）
- 修正コード: [lil_common_frag.hlsl](../Assets/lilToon/Shader/Includes/lil_common_frag.hlsl)
- 実機での比較手順: [Unity.md](Unity.md)

## 1. 症状と発生条件

Unity EditorのSceneビューおよびVRChatの鏡で、視点によって黒い斑点が発生する。主な再現時の設定は以下のとおり。

- ノーマルマップ1stが無効、2ndが有効。
- 異方性反射および適用先「反射」が有効。
- 光沢のタイプがリアル。

異方性反射用ノーマルマップのTilingと表示距離によって発生状況が変化する。詳細な発生条件は未特定であり、上記の設定が発生の必須条件であるとは限らない。

### マテリアル設定による切り分け

| 変更内容 | 結果 |
|---|---|
| 異方性反射を無効化 | 改善 |
| 異方性反射の適用先「反射」を無効化 | 改善 |
| 光沢をリアルからトゥーンに変更 | 改善 |
| 異方性反射の適用先「マットキャップ」を無効化 | 改善せず |
| 1st Specularのノイズ強度を0に変更 | 改善せず |
| 異方性反射強度の符号を反転 | 改善せず |

元マテリアルのテクセルや問題ピクセルの中間値は取得していない。

## 2. 原因の考察

### 異方性反射用タンジェントの縮退

元の実装では、異方性反射用の方向ベクトルをワールド座標系に変換し、正規化してから法線に対する直交化を行う。

```hlsl
fd.T = lilOrthoNormalize(normalize(mul(anisoTangent, fd.TBN)), fd.N);
fd.B = cross(fd.N, fd.T);
```

`lilOrthoNormalize()` は法線成分を引いて正規化する関数である。入力方向がゼロ、または法線と平行・反平行に近い場合、正規化の対象がゼロベクトルや極めて短いベクトルになる可能性がある。HLSLの `normalize(0)` の結果は不定である。

### 後続の光沢計算への影響

- Offset適用後の `normalize(T - N * shift)` でも縮退が起こり得る。
- タンジェントとバイタンジェントは両SpecularローブのGGX分布項およびSmithの可視性項（`lambdaV`、`lambdaL`）で使用される。分母に定数を加える処理だけでは、既に生じたNaNを回復できない。
- トゥーン光沢では後続の `lilTooningScale()` で `saturate()` を通る。リアル光沢ではフレネル項と反射色のアルファを掛けた値が `lilBlendColor()` の補間係数となる。Screen合成でも非有限値が色に伝播し得る。

光沢の戻り値からNaN・Infを除去すると黒い斑点が解消した実機検証結果と整合する。ただし、最初に異常値が発生する命令や、異常値が黒色として現れる段階は特定できていない。

### 入力ベクトルとシェーダーの処理経路

**ノーマルマップのデコード**

`Default.lilblock` の既定値は `bump`。サンプル機能が無効の場合、マクロ内では `(0.5, 0.5, 1.0, 0.5)` を使用する。

`lilUnpackNormalScale()` はRGB方式ではRGBを[-1, 1]に変換し、それ以外の方式ではAGからXYを復元し、平方根でZを求める。後者のうちASTC以外では先にAとRを乗算するため、上記の定数から得られるXは-0.5となる。テクスチャ未割当とサンプル機能無効は区別する必要がある。

**TBNと法線**

`LIL_GET_TBN_DATA` は補間後のタンジェント、符号付きバイタンジェント（`cross(N,T) * tangent.w * LIL_NEGATIVE_SCALE`）、法線を行として保持する。

normalパスの `fd.origN` は幾何法線を正規化した値であり、`fd.N` はノーマルマップ適用後の法線（無効時は幾何法線）を正規化し、裏面設定に応じて反転した値である。正規化後も丸め誤差は残る。

標準パスでは異方性反射用タンジェントの生成時点で `fd.T` と `fd.B` は初期値ゼロであるため、メッシュ由来の代替方向には `fd.TBN` を使用する必要がある。

**描画パス**

不透明・カットアウト・半透明系は共通の異方性処理を通る。normalパスではアルファ値の固定、カットオフ付近の被覆率計算やdiscard、clip、プリパスの早期returnなどに違いがある。屈折では半透明用clipや環境反射の合成方法が異なる。宝石は専用パスで環境反射を計算し、通常の `lilCalcSpecular()` を呼ばない。

## 3. 修正内容

異方性反射用の方向ベクトルを D、法線を N とし、外積を2回使用して接平面上の方向を求める。

```text
C = N × D
C × N = D(N · N) - N(D · N)
```

Nが単位ベクトルで入力が縮退していない場合、元の直交化処理と数学的に等価な方向が得られる。法線に多少の長さ誤差があっても、法線に垂直な方向を生成できる。

### 縮退判定

```hlsl
dot(C, C) <= max(1e-20f, 1e-8f * dot(D, D))
```

| 閾値 | 目的 |
|---|---|
| 相対下限 `1e-8f` | 単位法線の場合、法線と入力方向のなす角のsinが約1e-4以下となる場合を除外 |
| 絶対下限 `1e-20f` | 極めて小さい外積の二乗長を除外 |

### フォールバック

縮退時のみ、次の優先順位で代替方向を選択する。

1. メッシュ由来のタンジェント（`fd.TBN[0]`）。
2. メッシュ由来の符号付きバイタンジェント（`fd.TBN[1]`）。
3. 法線と平行にならない座標軸。

可能な限りメッシュに追従する方向を使用する。出力バイタンジェントは従来と同じ `cross(N, T)` で生成し、ミラーUVの符号は入力TBNで反映される。

変更範囲は異方性反射用タンジェントの生成処理に限定している。共通関数 `lilOrthoNormalize()`、光沢計算結果の値域、HDRの上限は変更していない。MatCapおよびMatCap 2ndにも新しい接線が渡る。

## 4. 検証結果

### Unity Editor・VRChatでの実機検証

投稿者による修正前後の比較では、検証した再現条件で黒い斑点が解消した。

| 項目 | 環境 |
|---|---|
| OS | Windows 11（Build 26300.9974） |
| CPU | AMD Ryzen 7 9800X3D |
| GPU | AMD Radeon RX 7900 XTX |
| GPUドライバー | 32.0.32029.2010 |
| Unity | 2022.3.22f1 |
| lilToon | 2.4.1 |
| Graphics API | Direct3D 11 |
| Feature Level（Unity Editor） | 11.1 |

髪・金属の異方性反射、アバター回転時の光沢、MatCap、VRChatの鏡についても、検証条件では問題がないことを目視で確認した。他のVRChatユーザーの環境でも黒い斑点の解消を確認したが、各ユーザーの詳細な動作環境は未確認である。

### 数値計算テスト

float32、乱数seed 7900で、100,000件のランダム入力と12件の境界条件を比較した。

| 評価項目 | 修正前 | 修正後 |
|---|---:|---:|
| 非有限値が発生したフレーム数 | 7 | 0 |
| 法線とタンジェントの内積の絶対値の最大値 | 約1.0 | 1.19e-7 |

修正後の主な指標は以下のとおり。

| 評価項目 | 最大値 |
|---|---:|
| タンジェントの長さ誤差 | 1.79e-7 |
| バイタンジェントの長さ誤差 | 9.54e-7 |
| 3組の基底ベクトル間の内積の絶対値 | 1.20e-7以下 |
| 通常のランダム入力における元実装との差 | 1.55e-5 |
| 回転追従誤差（ワールド座標軸へのフォールバック例を除く） | 1.84e-5 |

閾値付近で代替方向とマップ方向が直交する境界条件では、方向ベクトルの差の長さが約√2となった。

テストコード: [numeric.py](numeric.py) / 全計測結果: [numeric.txt](numeric.txt)

### シェーダーのコンパイル検証

DXC 1.9を使用し、元実装と修正後のタンジェント生成処理を抽出して、`ps_6_0` のピクセルシェーダーとしてコンパイルした。

| 評価項目（-O3） | 修正前 | 修正後 |
|---|---:|---:|
| DXILのSSA代入数 | 53 | 99 |
| 条件分岐数 | 0 | 3 |
| 逆平方根の演算数 | 2 | 1 |

追加された条件分岐のうち2つはフォールバック処理内にある。SSA代入数は静的な中間表現の比較であり、実際のGPU命令数や実行時間を示すものではない。

また、行継続を含むマクロ定義についても、スタブを使うピクセルシェーダーとしてコンパイルする検証コードを用意している。

テストコード: [compile.py](compile.py)、[compile_macro.py](compile_macro.py) / 計測結果: [compile.txt](compile.txt)

計測ログ内の修正版のコミット `6196ed2` と現在のPRの修正版 `3a5916e` では、検証に使用する `lil_common_frag.hlsl` と `lil_common_functions.hlsl` の内容が同一であることをblobハッシュにより確認済み。既存の計測ログは変更していない。

## 5. 制限事項・未確認事項

- 詳細な発生条件、問題ピクセルの中間値、ミップマップやテクスチャフィルタリングとの直接的な因果関係は未確認。
- 追加で確認された再現条件については、修正後の結果は未確認。
- 縮退判定の閾値が視覚的に最適であるかは未検証。フォールバック切り替えによる不連続性が生じる可能性がある。
- 両メッシュ軸が使用できない場合の回転追従や、ゼロ・非有限の法線、極端なオーバーフローは保証しない。
- ビュー方向と異方性軸の平行、`V + L = 0` など、別の計算箇所で発生する縮退は対象外。
- CPU上のfloat32テストとDXCの部分コンパイルだけでは、GPU上の演算結果やUnityの全シェーダーバリアントの動作を保証できない。
- GPU実行時間、ドライバー最適化の影響、異なるGPUメーカーやGraphics APIでの詳細な動作は未検証。

## 6. 検証資料の利用方法

リポジトリのルートディレクトリで実行する。

```sh
python3 investigation/numeric.py
python3 investigation/compile.py
python3 investigation/compile_macro.py
```

数値計算テストにはPython 3とNumPy、コンパイル検証にはPATH上のDXCが必要。

Unityでの比較方法は [Unity.md](Unity.md) を参照する。修正前のシェーダーに適用するパッチは [fix.patch](fix.patch)、独立した合成テスト用のノーマルマップは [directions.tga](directions.tga)。
